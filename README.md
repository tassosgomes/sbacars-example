# sbacars-example

Frontend foundation for the car sales platform described in [docs/vision.md](docs/vision.md).

## Structure

```text
apps/
  catalog/      # Public catalog (D01) + interest capture (D03)
  backoffice/   # Inventory (D02), leads (D03), purchase stub (D04)
packages/
  ui/           # Shared design system (tokens + primitives)
context/
  domain-map.md # Domain landscape (bounded contexts)
domains/
  catalogo-descoberta/   # D01
  estoque-curado/          # D02
  interesse-atendimento/   # D03
```

## Prerequisites

- Node.js 20+
- Docker (for local Logto OIDC in backoffice development)

## Setup

```bash
npm install
```

## Logto (backoffice OIDC)

The backoffice authenticates against a local, self-hosted [Logto](https://logto.io) instance —
the single identity provider for every environment (see
[`docs/architecture/backend-foundation.md`](docs/architecture/backend-foundation.md) §5.0).
Keycloak has been removed.

```bash
docker compose up -d postgres logto-db-init logto-seed logto
```

This provisions the dedicated `logto` Postgres database, seeds Logto's internal schema
(idempotent — safe to rerun) and starts the server: OIDC on
[http://localhost:3001](http://localhost:3001), admin console on
[http://localhost:3002](http://localhost:3002). State lives in Postgres, so
`docker compose down` followed by `up` does not lose data (unlike the old Keycloak `start-dev`
setup, which reimported its realm JSON on every restart).

The API resource, SPA application, roles and dev users are **not** created by `docker compose up`
— they come from an idempotent Management API bootstrap script that needs a one-time manual step
(creating a Machine-to-Machine application in the Logto console; self-hosted Logto has no API to
create that first M2M app for itself). Full instructions, including that manual step, are in
[`infra/logto/README.md`](infra/logto/README.md). Short version once the manual step is done:

```bash
export $(grep -v '^#' infra/logto/.env | xargs)
node infra/logto/bootstrap.mjs
```

OIDC client: `backoffice` (SPA, Authorization Code + PKCE). The `client_id` is generated by Logto
(not chosen, unlike Keycloak) and written into `apps/backoffice/public/runtime-env.js` by the
bootstrap script. Authority: `http://localhost:3001/oidc`. Every login requests the API resource
`https://api.sbacars.app`, so the access token carries `aud: https://api.sbacars.app` and the
scopes granted to the signed-in user's role — see §5.1/§5.2 of the foundation plan.

## Development

```bash
# Public catalog — http://localhost:5173
npm run dev:catalog

# Backoffice — http://localhost:5174
npm run dev:backoffice
```

Backoffice auth flow: open the app → **Sign in** → Logto login → redirect to `/auth/callback` → dashboard. **Sign out** in the header ends the Logto session and returns to `/login`.
