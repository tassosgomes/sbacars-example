# ADR-006: Tipos gerados do contrato com openapi-typescript, hooks escritos à mão

## Status

Proposed

## Data

2026-08-16

## Contexto

O `api-contract.yaml` tem 17 endpoints e cerca de 45 schemas, incluindo enums que carregam regra de
negócio (`SituacaoOferta`, `EstadoDisponibilidade`, `TipoSolicitacao`, `CodigoCriterio`) e uma
união discriminada por `tipo` em `AbrirSolicitacaoInput`.

Escrever esses tipos à mão no frontend é dívida técnica garantida: qualquer alteração do contrato
passa a exigir uma edição espelhada que nada obriga a acontecer, e a divergência só aparece em
runtime.

A questão não é *se* gerar — é **o quanto** gerar. Duas famílias de ferramenta:

- geradores de **tipo apenas** (`openapi-typescript`), que produzem um `.d.ts` e deixam o cliente
  HTTP por nossa conta;
- geradores de **cliente completo** (`orval`, `kubb`), que produzem também os hooks do TanStack
  Query, um arquivo por operação.

Três características do D02 pesam nessa escolha:

1. **O `apiFetch` precisa anexar o `Authorization`** lendo o token do `UserManager` do
   `react-oidc-context`. Em gerador de cliente, isso vira um "mutator" configurado no gerador.
2. **O `409` de `suspensao-nao-confirmada` não é erro** — é uma mutação em duas fases (ADR-003).
   O hook precisa interceptar esse código específico e devolver `criteriosAfetados` ao componente.
3. **`AbrirSolicitacaoInput` é uma união discriminada** com quatro variantes e payloads diferentes.
   Gerador de cliente costuma achatar isso num tipo único com todos os campos opcionais, o que
   perde exatamente a garantia que a união dá.

## Decisão

Usar **`openapi-typescript`** para gerar apenas os tipos, e escrever os hooks do TanStack Query à
mão sobre o `apiFetch`.

```bash
npx openapi-typescript tasks/prd-gestao-do-estoque-curado-e-disponibilidade/api-contract.yaml \
  -o apps/backoffice/src/shared/api/schema.d.ts
```

- O comando vira o script `npm run gen:api -w @sbacars/backoffice`.
- `schema.d.ts` é **commitado** e nunca editado à mão; um cabeçalho gerado marca isso.
- O CI regenera e falha se o arquivo commitado divergir do contrato — é o que impede o drift
  silencioso que motivou a decisão.
- Aliases de domínio ficam num `types.ts` próximo, para o resto do código não escrever
  `components['schemas']['…']` em toda linha:

  ```ts
  import type { components } from './schema';
  export type OfertaDetalhe = components['schemas']['OfertaDetalhe'];
  export type SituacaoOferta = components['schemas']['SituacaoOferta'];
  ```

## Alternativas Consideradas

### Alternativa 1: orval

- **Descrição:** gera tipos **e** hooks do TanStack Query a partir do contrato.
- **Prós:** elimina o código de cliente escrito à mão. Um endpoint novo no contrato vira um hook
  novo sem trabalho. Forte quando o consumo é uniforme.
- **Contras:** gera cerca de 40 arquivos que entram no repositório e no code review sem serem
  lidos. Auth e tratamento de erro passam a ser configuração do gerador (um "mutator"), não código
  nosso — e o caso do `409` em duas fases é fora do padrão o bastante para virar um mutator com
  lógica de negócio dentro, num arquivo que ninguém associa a regra de negócio. A união
  discriminada de `AbrirSolicitacaoInput` tende a ser achatada.
- **Por que rejeitada:** os três pontos onde o D02 foge do consumo uniforme — auth, `409` em duas
  fases e união discriminada — são exatamente onde o gerador de cliente cobra o preço. Ganharíamos
  automação nos 14 endpoints simples e perderíamos clareza nos 3 que importam.

### Alternativa 2: kubb

- **Descrição:** semelhante ao orval, com plugins mais modulares e saída mais controlável;
  pode gerar schemas zod junto.
- **Prós:** gerar zod do contrato eliminaria o drift entre validação de formulário e contrato,
  que é o risco assumido no ADR-007.
- **Contras:** ecossistema menor e menos maduro. Os schemas zod gerados refletem o contrato, mas o
  D02 tem validações de UI que **não** estão no contrato (a regra condicional da T04, por exemplo,
  está descrita em prosa no `description`, não em JSON Schema) — os zod gerados precisariam ser
  estendidos, o que recria a fronteira gerado/manual em outro lugar.
- **Por que rejeitada:** o benefício real (zod gerado) resolve o risco do ADR-007 só parcialmente,
  e a maturidade menor pesa numa decisão que vira precedente para o `catalog`.

### Alternativa 3: escrever os tipos à mão

- **Por que rejeitada:** anti-pattern explícito da skill `tsg-flow-frontend-techspec-creator`.
  Não foi considerada de fato.

## Consequências

### Positivas

- Uma única fonte de verdade para tipos, com o CI provando que ela é respeitada.
- Os hooks são código normal, legível e testável — incluindo o do `409` em duas fases, que fica
  onde alguém procuraria por ele.
- O diff de uma mudança de contrato é legível: um arquivo gerado muda, e os hooks afetados quebram
  no `tsc`.
- Nada impede migrar para orval depois; o inverso (sair de código gerado) é mais caro.

### Negativas

- Cada endpoint exige um `queryFn`/`mutationFn` escrito à mão — 17 funções pequenas.
- `schema.d.ts` é um arquivo grande no repositório, ruidoso em diffs de contrato.
- A tipagem via `components['schemas'][...]` é verbosa sem a camada de aliases.

### Riscos

- **Alguém editar `schema.d.ts` à mão** para "consertar" um tipo. Mitigação: cabeçalho de arquivo
  gerado, entrada no `.eslintignore`, e a checagem de CI que reverteria a edição no próximo
  `gen:api`.
- **O contrato mudar e ninguém rodar o gerador.** Mitigação: é exatamente o que o passo de CI pega
  — regenera e compara.

## Notas de Implementação

- `openapi-typescript` fica em `devDependencies`; nada dele vai para o bundle.
- O `schema.d.ts` é `.d.ts` puro: não gera JavaScript e some do build.
- Os enums do contrato viram uniões de string literal, o que dá exaustividade em `switch` —
  aproveitar isso nos mapas de badge (situação, disponibilidade, tipo de solicitação) para que um
  valor novo no contrato quebre o build em vez de renderizar um badge sem cor.
