# ADR-002: Oferta e Solicitacao como agregados separados

## Status

Proposed

## Data

2026-08-16

## Contexto

O domain doc do D02 lista oito entidades: Veículo, Oferta curada, Estoque curado, Origem
conhecida, Condição conhecida, Histórico disponível, Preço oficial e Disponibilidade
operacional. A UX spec acrescenta a Solicitação pendente, tratada como entidade única
discriminada por `tipo` (DUX-03).

Traduzir isso um-para-um em agregados produziria oito raízes e transações distribuídas para
qualquer operação real. É preciso escolher fronteiras de consistência, não espelhar o
vocabulário.

Duas forças definem o recorte:

**A regra de suspensão exige avaliação atômica.** O RF-03 determina que, quando uma alteração
faz uma oferta elegível deixar de cumprir um critério mínimo, sua elegibilidade é suspensa na
mesma operação. Os seis critérios (CM-1 a CM-6) leem identificação, dados básicos, localização,
preço oficial, disponibilidade e os três blocos de fatos. Se esses dados estivessem espalhados
por vários agregados, a avaliação seria uma leitura cross-agregado dentro de uma escrita — a
condição clássica para inconsistência sob concorrência.

**A fila de validação é uma consulta cross-oferta.** `GET /solicitacoes` lista solicitações de
todas as ofertas, ordenadas por idade, com filtro por tipo e status. É uma projeção, não a
navegação de um agregado.

## Decisão

Dois agregados:

```text
Oferta (AggregateRoot)
 ├─ Veiculo          entidade filha
 ├─ FatosConhecidos  value object com três blocos (origem, condicao, historico)
 ├─ PrecoOficial     value object
 ├─ Disponibilidade  value object
 ├─ Situacao         enum
 └─ AvaliarCriteriosMinimos() → suspende quando aplicável

Solicitacao (AggregateRoot)
 ├─ OfertaId         referência por id, nunca por navegação
 ├─ Tipo, Status, Justificativa
 ├─ AbertaPor, Decisao
 └─ Aprovar(usuarioId) / Rejeitar(usuarioId, justificativa)
```

`Estoque curado` do domain doc **não vira agregado**: é o conjunto de Ofertas, expresso como
consulta, não como objeto. Origem, Condição e Histórico não viram entidades próprias — são os
três blocos do value object `FatosConhecidos`, porque não têm identidade nem ciclo de vida
independentes da oferta.

A regra de suspensão vive em `Oferta.AvaliarCriteriosMinimos()`, dentro do agregado, e é
chamada por toda mutação que possa afetá-la.

Solicitação referencia Oferta **por id**. A aplicação da alteração aprovada carrega os dois
agregados na mesma transação e chama o método de negócio correspondente na Oferta — não há
navegação de objeto entre eles.

## Alternativas Consideradas

### Alternativa 1: Solicitacao como entidade filha de Oferta

- **Descrição:** um único agregado `Oferta`, com uma coleção de `Solicitacoes`.
- **Prós:** a invariante "no máximo uma pendência aberta por tipo" (DUX-07) fica garantida
  dentro do agregado, sem consulta extra nem índice único. A aprovação seria uma única
  transação sobre um único agregado.
- **Contras:** a fila de validação — que é a tela principal de um dos dois papéis do produto —
  exigiria varrer ofertas para listar solicitações. Ou se carregam agregados inteiros para
  exibir sete linhas, ou se cria uma query que ignora o agregado, admitindo que a fronteira
  estava errada.
- **Por que rejeitada:** o custo cai justamente sobre o fluxo de trabalho do Responsável de
  validação, que tem meta de SLA no PRD. A invariante que se ganharia é barata de garantir de
  outro jeito (índice único parcial em `(oferta_id, tipo)` restrito a `status = 'pendente'`).

### Alternativa 2: Veiculo como agregado separado de Oferta

- **Descrição:** seguir a literalidade do domain doc, onde Veículo e Oferta curada são
  entidades distintas ligadas por "pode compor".
- **Prós:** fiel ao vocabulário do domínio. Abriria caminho para um veículo compor mais de uma
  oferta ao longo do tempo.
- **Contras:** na Fase 1 a relação é sempre 1:1 — o cadastro cria os dois juntos e nada os
  separa. Separar obrigaria transação entre dois agregados só para avaliar CM-1 e CM-2, que
  leem dados do veículo.
- **Por que rejeitada:** YAGNI. A cardinalidade N:1 não existe em nenhum requisito da Fase 1,
  e o custo é pago em toda avaliação de critério mínimo. Se a Fase 3 trouxer estoque real com
  reaproveitamento de veículo, extrair depois é um refactor local.

### Alternativa 3: Um agregado por entidade do domain doc

- **Descrição:** oito raízes espelhando o vocabulário.
- **Por que rejeitada:** tornaria qualquer operação real uma transação distribuída. Domain doc
  descreve linguagem de negócio, não fronteiras de consistência.

## Consequências

### Positivas

- A suspensão automática do RF-03 é uma decisão local, dentro de um agregado, numa transação.
  Não há janela em que a oferta esteja elegível com critério quebrado.
- A fila de validação é uma query direta sobre uma tabela, com índice por `status` e
  `aberta_em` — barata e naturalmente paginável.
- `GET /ofertas/{id}` carrega um agregado e monta a resposta inteira do contrato, o que
  justifica a decisão de a tela de detalhe ser uma chamada só.
- O agregado Oferta é o único lugar onde a situação muda, o que torna a máquina de estados
  testável sem banco.

### Negativas

- A invariante "uma pendência aberta por tipo" passa a depender de índice único no banco, não
  do modelo. Uma corrida entre duas aberturas simultâneas é resolvida pelo banco, e o
  handler precisa traduzir a violação de unicidade em 409.
- Aprovar uma solicitação toca dois agregados na mesma transação — aceitável porque são locais
  ao mesmo serviço e ao mesmo schema, mas é uma exceção à regra "um agregado por transação".
- O agregado Oferta é grande: veículo, três blocos de fatos, preço e disponibilidade. Carregá-lo
  para alterar só a disponibilidade é mais caro do que carregar uma linha.

### Riscos

- **Contenção no agregado Oferta.** Operador e Responsável podem tocar a mesma oferta em
  paralelo. Mitigação: token de concorrência otimista (`xmin` do PostgreSQL) na Oferta;
  conflito vira 409, não last-write-wins silencioso.
- **A exceção "dois agregados numa transação" virar hábito.** Mitigação: registrar que ela
  existe só no caminho de aprovação, e que o motivo é a alteração aprovada ser, por definição,
  a aplicação de uma decisão sobre outra entidade.

## Notas de Implementação

- Value objects herdam de `SbaCars.BuildingBlocks.Domain.ValueObject`; `Oferta` e
  `Solicitacao` de `AggregateRoot`, que já mantém a lista de eventos de domínio pendentes.
- `FatosConhecidos` expõe `AtendeTransparencia` por bloco — é o cálculo do CM-6, e o contrato
  o devolve pronto para a interface não reimplementá-lo.
- `Disponibilidade` expõe `TransicoesPermitidas`, derivado do estado atual. É a mesma máquina
  de estados que valida a transição na escrita e que alimenta os botões da tela.
- Índice único parcial: `CREATE UNIQUE INDEX ... ON inventory.solicitacao (oferta_id, tipo)
  WHERE status = 'pendente'`.
- Índice único parcial na placa: `... ON inventory.oferta (placa) WHERE situacao <> 'retirada'`,
  que é o que permite recadastrar depois de uma retirada (QA-01).
