# ADR-005: TanStack Query como camada de server state do backoffice

## Status

Accepted

## Data

2026-08-16

## Contexto

O `apps/backoffice` hoje não tem **nenhuma** biblioteca de dados: sem React Query, sem SWR, sem
Redux, sem Zustand. O único ponto de rede é `apiFetch`, que prefixa a base URL e nada mais — nem
anexa o header `Authorization`. Nenhuma tela consome API ainda; as quatro páginas existentes são
`EmptyState`.

O D02 é o primeiro consumo real, e o padrão de invalidação dele é agressivo. Três exemplos
concretos, retirados do `ux-spec.md` e do `api-contract.yaml`:

1. **Aprovar uma solicitação invalida três coisas ao mesmo tempo:** a fila (`GET /solicitacoes`),
   o badge da sidebar (`GET /solicitacoes/pendentes/contagem`) e o detalhe da oferta afetada
   (`GET /ofertas/{id}`), que mudou de situação. A fila e o badge vivem em telas diferentes.
2. **O badge da sidebar é polling.** O `x-frontend-notes` do contrato pede 60s, e ele aparece em
   toda tela do backoffice.
3. **A T03 é uma carga única reutilizada por vários modais.** M05, M05-b e M06 mutam e precisam
   refletir no mesmo `OfertaDetalhe` que a tela já tem em mãos.

O protocolo de suspensão do ADR-003 acrescenta um padrão fora do comum: uma mutação que retorna
`409` e precisa ser **repetida** com `confirmaSuspensao: true` depois de uma confirmação do
usuário. Isso é uma mutação em duas fases, não um erro terminal.

## Decisão

Adotar **TanStack Query v5** como única camada de server state.

- Um `QueryClient` na raiz do app, com `staleTime` padrão de 30s e `retry: 1`.
- Chaves hierárquicas: `['ofertas']`, `['ofertas', id]`, `['solicitacoes']`,
  `['solicitacoes','pendentes','contagem']` — a hierarquia é o que torna a invalidação por prefixo
  correta sem enumerar chaves.
- Toda mutação declara suas invalidações explicitamente no `onSuccess`.
- **Nenhuma biblioteca de client state.** O estado de cliente do D02 é filtro de lista, abertura de
  modal e estado de formulário. Filtro vai para a query string da URL (torna a triagem do operador
  compartilhável e sobrevive ao refresh); modal e formulário são estado local do componente.
  Introduzir Zustand ou Redux aqui seria abstração sem problema correspondente.

O `apiFetch` ganha o header `Authorization`, lendo o access token do `UserManager` do
`react-oidc-context`. É o único lugar que precisa saber disso.

## Alternativas Consideradas

### Alternativa 1: Hooks próprios sobre `apiFetch`

- **Descrição:** `useState` + `useEffect` encapsulados em um hook por endpoint, sem dependência
  nova.
- **Prós:** zero peso adicional no bundle. Nenhuma API nova para a equipe aprender. Controle total.
- **Contras:** cache, deduplicação de requisições concorrentes, revalidação em foco, retry e —
  principalmente — **invalidação cruzada entre telas** viram código nosso. O caso de aprovar uma
  solicitação exigiria um mecanismo próprio de notificação entre a fila e o badge da sidebar, que
  é literalmente reimplementar um query cache.
- **Por que rejeitada:** o D02 tem invalidação cruzada em quase toda mutação. O código que
  economizamos em dependência gastamos em infraestrutura de sincronização mal testada.

### Alternativa 2: SWR

- **Descrição:** biblioteca menor (~4kb gz contra ~13kb), cobre cache e revalidação.
- **Prós:** menor, API mais enxuta, suficiente para leitura.
- **Contras:** a API de mutação (`useSWRMutation`) e a invalidação por chave são mais cruas —
  invalidar por prefixo exige um matcher próprio. O D02 é majoritariamente **escrita com efeito
  colateral em várias telas**, que é justamente onde o SWR oferece menos.
- **Por que rejeitada:** a economia de 9kb não compensa perder invalidação hierárquica num app
  cujo padrão dominante é mutação com efeito cruzado.

### Alternativa 3: RTK Query

- **Descrição:** camada de dados do Redux Toolkit.
- **Prós:** integra server e client state num único store.
- **Contras:** traz Redux junto, e não há client state global no D02 que justifique um store.
- **Por que rejeitada:** resolveria um problema que este app não tem, ao custo de uma dependência
  estrutural.

## Consequências

### Positivas

- Estados de `loading`, `error`, `empty` e `refetching` vêm prontos — e a `react-code-quality`
  exige que os três primeiros sejam tratados em toda tela.
- A invalidação cruzada de aprovar/rejeitar é declarativa e fica visível no `onSuccess` da mutação.
- O polling do badge é uma linha (`refetchInterval`), não um `setInterval` com limpeza manual.
- Requisições concorrentes para a mesma chave são deduplicadas — relevante porque `OfertaDetalhe`
  é consumido pela tela e por três modais simultaneamente.

### Negativas

- +13kb gzip no bundle e uma API nova para a equipe.
- É o primeiro padrão de dados do repositório: o `catalog` vai herdá-lo, e ele é um app **público
  e anônimo**, com necessidades diferentes (SSR-friendly, cache longo). A decisão precisa ser
  revisitada lá, não copiada.
- Chaves de query mal escolhidas produzem invalidação silenciosamente incompleta — um bug que não
  quebra teste unitário.

### Riscos

- **Invalidação incompleta após mutação.** É o modo de falha típico: o usuário aprova, a fila
  atualiza, o badge não. Mitigação: teste de integração com MSW cobrindo aprovar → fila e badge
  atualizados; a lista de invalidações de cada mutação é revisada no code review.
- **`staleTime` global mascarar dado velho** numa tela de operação. Mitigação: 30s é curto o
  bastante para operação humana; telas com decisão (T07, T08) usam `staleTime: 0`.

## Notas de Implementação

- `QueryClientProvider` acima do `AppAuthProvider` em `main.tsx`.
- O `retry: 1` global não se aplica a mutações — mutação com efeito colateral não é repetida
  automaticamente. `409` e `422` nunca são retentados.
- O `409` de `suspensao-nao-confirmada` **não é erro de UI**: a mutação o intercepta, o componente
  abre o diálogo e reexecuta com `confirmaSuspensao: true`. É fluxo, não falha.
- O OpenTelemetry já instrumenta `fetch` globalmente (`src/telemetry/index.ts`); TanStack Query usa
  o `fetch` global por baixo do `apiFetch`, então o `traceparent` continua saindo sem configuração
  extra.
