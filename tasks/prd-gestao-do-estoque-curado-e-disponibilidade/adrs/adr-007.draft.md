# ADR-007: react-hook-form + zod para os formulários do backoffice

## Status

Proposed

## Data

2026-08-16

## Contexto

O D02 tem três formulários de peso, e um deles tem uma regra que os outros não têm:

| Tela | Forma | Dificuldade |
|---|---|---|
| T02 — Cadastro de veículo | ~14 campos em 4 seções | **Salvar com campos vazios é o caminho feliz**, não erro (RF-01). Nenhum campo é obrigatório para gravar; a ausência apenas mantém a oferta em preparação |
| T04 — Fatos conhecidos | 3 blocos idênticos | Cada bloco tem um switch `informação indisponível` que **torna `limitacaoDeclarada` obrigatória** e colapsa os outros campos |
| M05 / M05-b / M06 | 1 a 3 campos | Simples |

A regra da T04 é condicional dentro de um objeto aninhado, repetida três vezes. E a da T02 é o
oposto do padrão: validação de formato (placa, ano, quilometragem) sim, obrigatoriedade não.

O `apps/backoffice` não tem biblioteca de formulário nem de validação hoje.

## Decisão

Adotar **react-hook-form** com **zod** via `@hookform/resolvers`.

A regra condicional da T04 vira um `refine` no schema do bloco, escrito uma vez e reusado três
vezes:

```ts
const blocoFatoSchema = z
  .object({
    indisponivel: z.boolean(),
    descricao: z.string().max(2000).optional(),
    fonte: z.string().max(300).optional(),
    evidenciaId: z.string().uuid().nullable().optional(),
    limitacaoDeclarada: z.string().max(1000).optional(),
  })
  .refine((b) => !b.indisponivel || !!b.limitacaoDeclarada?.trim(), {
    message: 'Declare a limitação quando a informação estiver indisponível.',
    path: ['limitacaoDeclarada'],
  });

export const fatosSchema = z.object({
  origem: blocoFatoSchema,
  condicao: blocoFatoSchema,
  historico: blocoFatoSchema,
});
```

O schema da T02 valida **formato**, nunca presença:

```ts
export const veiculoSchema = z.object({
  placa: z.string().regex(/^[A-Z]{3}-?\d[A-Z0-9]\d{2}$/, 'Placa inválida').optional().or(z.literal('')),
  anoFabricacao: z.coerce.number().int().min(1950).max(2100).optional(),
  quilometragem: z.coerce.number().int().min(0).optional(),
  tipoVeiculo: z.enum(['carro-seminovo', 'carro-usado']),
  // …
});
```

Os schemas zod vivem em `schemas.ts` dentro de cada feature, ao lado do formulário que os usa.
Cada um é tipado contra o tipo gerado do contrato, para que uma divergência quebre o `tsc`:

```ts
import type { VeiculoInput } from '@shared/api/types';
type _Check = z.infer<typeof veiculoSchema> extends VeiculoInput ? true : never;
```

## Alternativas Consideradas

### Alternativa 1: react-hook-form sozinho, sem zod

- **Descrição:** validação pelas regras do próprio RHF (`register(..., { validate })`).
- **Prós:** uma dependência a menos (~13kb gz de zod). Suficiente para formulários simples.
- **Contras:** a regra condicional da T04 vira um `validate` por campo, que precisa ler outro
  campo do mesmo objeto — espalhando a regra por três lugares e repetindo-a três vezes, uma por
  bloco. O schema deixa de existir como objeto, então não há como confrontá-lo com o tipo gerado
  do contrato.
- **Por que rejeitada:** perde a checagem contra o contrato, que é o que mantém o formulário e a
  API alinhados sem disciplina humana.

### Alternativa 2: Estado controlado à mão

- **Descrição:** `useState` por campo e uma função de validação própria.
- **Prós:** zero dependência.
- **Contras:** 14 `useState` na T02, com re-render do formulário inteiro a cada tecla; `touched`,
  `dirty` e mensagens de erro implementados na mão em três telas.
- **Por que rejeitada:** volume de código repetitivo desproporcional ao que se economiza.

### Alternativa 3: gerar os schemas zod do contrato (kubb, openapi-zod-client)

- **Descrição:** derivar os schemas de validação do próprio `api-contract.yaml`.
- **Prós:** eliminaria por construção o drift entre validação de formulário e contrato — o risco
  principal desta decisão.
- **Contras:** a regra da T04 **não está expressa em JSON Schema** no contrato; ela vive na prosa
  do `description` de `BlocoFatoInput` ("Obrigatória quando `indisponivel` é `true`"). Um schema
  gerado precisaria ser estendido à mão de qualquer forma, recriando a fronteira gerado/manual
  dentro do mesmo arquivo — que é pior do que tê-la entre arquivos.
- **Por que rejeitada:** resolveria o drift só parcialmente e complicaria justamente o formulário
  mais difícil. A checagem de tipo contra `VeiculoInput`/`FatosInput` cobre a maior parte do risco
  a um custo muito menor.

## Consequências

### Positivas

- A regra condicional da T04 fica escrita **uma vez**, num lugar onde se lê como a regra de
  negócio que é (RN-03).
- RHF usa componentes não controlados: digitar num dos 14 campos da T02 não re-renderiza os outros.
- A checagem `z.infer<…> extends VeiculoInput` faz uma divergência entre formulário e contrato
  falhar no `tsc`, não em produção.
- zod também serve para validar o `RUNTIME_ENV` na inicialização, se um dia for preciso.

### Negativas

- Duas dependências novas (RHF ~9kb, zod ~13kb gz).
- Os schemas zod são escritos à mão e podem divergir do contrato em regras que a checagem de tipo
  não pega — `maxLength`, `pattern` e `minimum` não aparecem no tipo TypeScript gerado.
- `z.coerce.number()` em campos numéricos opcionais tem armadilhas com string vazia; exige cuidado
  e teste.

### Riscos

- **Drift de restrição não tipada.** O contrato diz `maxLength: 1000` em `justificativa`; o tipo
  gerado diz só `string`. Se o contrato mudar para 2000, nada quebra e o formulário continua
  cortando em 1000. Mitigação: as restrições numéricas do contrato ficam em constantes num único
  módulo, comentadas com a origem; o code review de qualquer mudança de contrato inclui esse
  arquivo. É mitigação por processo, não por ferramenta — assumido conscientemente.
- **Validação de UI divergir da validação de domínio.** O backend é a autoridade (o `422` é a
  verdade). O formulário valida para dar feedback rápido, nunca para substituir o servidor.

## Notas de Implementação

- `zodResolver` de `@hookform/resolvers/zod`.
- Modo de validação `onBlur` nos formulários longos (T02, T04) e `onChange` nos modais curtos —
  validar a cada tecla nos 14 campos da T02 é ruído.
- O `submit` da T02 **nunca** é bloqueado por campo vazio; só por formato inválido. Um teste
  cobre exatamente isso, porque é o comportamento mais fácil de quebrar sem querer.
- Valores monetários: o formulário trabalha com string formatada em BRL e converte para centavos
  no envio, por um util único em `shared/`. O contrato só conhece centavos.
